# 青盈每日内容个性化推荐修改方案

HSTU 推荐算法与工程实施说明

版本 1.0　日期 2026 年 10 月 13 日　适用范围 今天页面的每天一期音频博客

## 1 修改目的与预期结果

本次修改拟将“每天一期”的推荐依据扩展为用户当前财务状态与内容偏好：综合账本收支、储蓄目标、未来开支和历史反馈，每天从已审核的真实单集中选择一期，并给出可核对的推荐理由。推荐核心采用 HSTU 序列模型；财务统计由后端确定性计算，作为模型的上下文输入。

目标是让内容随用户实际需要变化。例如，同一个用户的内容兴趣保持不变，但近期新增考试费、目标期限临近，推荐应能够转向资金安排相关内容。是否能达到这一效果，要通过本项目的离线评估与线上实验验证，不能直接套用论文的效果数字。

### 现有功能与需要补足的部分

当前 podcast_service.py 的 _interest 主要读取学习主题、问卷、近期练习及少量消费类别；_pick 使用主题匹配、字符哈希向量相似度、质量、新鲜度和重复惩罚进行固定加权。推荐尚未直接综合储蓄目标进度、开支到期日与资金缺口。

现有工程已有目标规划、未来开支、收支汇总、审核目录和每日推荐缓存，可作为改造基础。本次方案增加财务特征、可训练的排序器和完整反馈链路，不要求重建整个应用。

### 用户可见的结果

- 每个用户按个人时区每天最多得到一期推荐；当天多次打开保持稳定。
- 展示单集标题、真实链接、简介和具体推荐理由；可查看理由依据并纠正数据。
- 增加“对我有帮助”反馈；保留收藏和不感兴趣。
- 无合适候选时显示明确的空状态；数据不足时使用可解释的回退结果。

### 修改边界

本方案面向推荐已有音频博客单集。自动生成文章、合成音频、短信或系统通知属于另行开发范围；本次“推送”首先指今天页面的站内展示。所有模块、表结构和参数均为拟实施设计，现有事实会单独标注。

## 2 应用算法与 AI 职责

### 核心算法 HSTU

HSTU 的全称为 Hierarchical Sequential Transduction Unit，是 Meta 在 2024 年提出的序列推荐架构，属于生成式推荐研究路线。它将用户交互序列编码为用户表示，用于预测或排序候选内容。官方实现提供上下文、内容和行为特征的接入结构。[1][2][3]

本项目采用“HSTU 编码加候选评分”的形式：给定用户财务上下文、过去的内容交互和当前候选单集，输出每个候选的相关预测值，再选择一个真实单集 ID。生成式推荐不等于生成文章；这里不让模型凭空生成标题或链接。

财务上下文接入、教育内容目标函数、新内容编码和推荐理由属于本项目扩展。HSTU 本身没有预置大学生财务分析功能，也不能通过配置模型名称直接获得可用推荐结果，必须准备数据并训练。

### 为什么采用这一方向

HSTU 能建模行为的顺序和时间，适合学习用户从某个主题转向另一个主题的过程。通过上下文输入，可以测试“同样的内容历史，不同的财务状态”是否应产生不同结果。其开源实现与 NVIDIA 部署示例提供工程起点。[2][3][4]

HSTU 是本项目选择的先进架构，不是所有数据集上的统一最优算法。原始工作发布于 2024 年；2026 年的部署进展说明工程工具仍在更新，不能据此声称它是最新发表或全球最强的方法。

### 各组件的职责

| 组件 | 输入与输出 | 职责 |
| --- | --- | --- |
| 财务计算服务 | 原始记录 → 统计与规划事实 | 计算金额、期限、缺口与数据覆盖情况 |
| 内容编码器 | 标题简介主题 → 内容表示 | 支持语义匹配和新单集接入 |
| HSTU 排序器 | 财务上下文加行为序列加候选 → 预测值 | 学习当前用户与单集的匹配关系 |
| 资格与选择规则 | 候选预测值 → 当日单集 | 执行审核、拒绝、去重与每日一期约束 |
| 理由生成器 | 已核验事实加单集主题 → 中文理由 | 首版采用模板；通用大模型仅作可选文案增强 |

通用语言模型不是本次推荐的核心算法。即使以后加入语言模型，它也只接收必要摘要，输出必须与事实和单集 ID 一致；解释不作为模型因果依据或财务计算结果。

## 3 财务特征如何进入推荐

### 构建有时间戳的财务快照

新增 finance_context_service，读取经过授权的本用户数据，生成不可变的推荐时点快照。复用 user_data_service 的汇总能力与 goal_planner 的现金流规划逻辑，补充推荐专用统计。快照保存 as_of、用户时区、数据版本、读取范围及缺失标记。

| 数据组 | 建议特征 | 计算与使用要求 |
| --- | --- | --- |
| 收支记录 | 本月及最近 7 日净支出；30 日类别占比；最近两段 30 日变化；记录笔数 | 当月汇总可复用现有接口；滚动窗口需要新增查询；不足完整窗口时不计算同比式变化 |
| 收入 | 已记录收入；用户填写的月收入；预计到账日 | 实际收入与预计收入分开；自己的账户间转账不重复计入收入 |
| 储蓄目标 | 剩余金额；剩余天数；完成比例；规划缺口；活跃目标数量 | 复用经过验证的规划结果；共享资金不可重复分配到多个目标 |
| 未来开支 | 7 日与 30 日到期金额；最近到期天数；未处理事项数量 | 已处理或已实际支付的事项需对账，避免再次预留 |
| 可用资金 | 余额快照；必要开支；应急预留；规划后的剩余资金 | 余额日期与账本口径必须一致；未知余额不推断成零 |
| 数据质量 | 缺失标记；读取是否完整；记录天数；余额是否过期 | 作为模型输入和理由展示条件，控制结论强度 |

### 编码方式

金额类非负特征可使用 log1p 缩放；净结余等有正负号的特征使用保留符号的对数缩放。比例限定合理范围，日期转换为距离推荐日的天数并裁剪异常值。归一化参数只从训练集计算，线上使用同版本参数。

连续特征与缺失掩码经小型 MLP 映射为上下文向量；目标类型、主题和状态经类别嵌入编码。首版使用固定顺序的汇总上下文，不把每笔账单直接当成“喜欢某一期内容”的交互标签。

### 财务计算口径

以分为整数单位计算金额，输出时转为元。退款关联原支出类别；内部转账与借款分别标记，避免误当成工资。趋势只表示已记录数据变化，不把单笔购物解释成冲动消费或能力不足。

按开支到期日和预计收入到账日进行时间线检查。预计收入不能充当今天已到账余额；已存目标金额如果已包含在账户余额中，应先扣除占用，若保存在独立账户则明确排除。复用现有规划器前须检查其收支覆盖范围，补齐未覆盖交易类型。

## 4 每日推荐的在线流程

财务快照 → 候选过滤 → HSTU 评分 → 每日一期

### 请求与候选准备

1. GET /api/podcasts/today 从认证信息取得用户 ID，按用户时区确定日期。若已有有效日推荐，直接返回。
2. 读取目录与用户数据的版本，构建财务快照和内容交互历史。数据查询失败与空记录分开处理。
3. 先过滤未审核、链接失效、包含商业推广、语言或难度不适合的内容，并排除明确拒绝的单集。
4. 目录较小时对全部合格单集评分；目录扩大后再用主题和内容向量召回候选。候选数量起始上限建议为 100，按覆盖率与延迟调整。

### 评分与当日选择

5. 用 HSTU 编码财务上下文和截至推荐时点的内容序列，针对候选预测点击、收藏、明确有帮助和不感兴趣的概率。未收集到的反馈任务不启用。
6. 以有帮助预测为主要方向，结合收藏、负反馈和内容适配计算效用；权重由验证集和线上实验决定。不得把模型分数直接称为用户财务改善概率。
7. 首版将最近 30 日已推荐单集作为排除项，这是对现有“重复惩罚”逻辑的拟修改。过滤后无候选则显示空状态，避免为了填满卡片重复内容。
8. 从事实快照和单集标签中选取一至两条匹配依据，生成理由。例如“你记录了近期需要预留的开支，这一期介绍按到期日安排资金的方法”。证据不足时使用一般学习理由。

### 持久化与并发

模型推理在数据库写事务之外执行，避免在现有 SQLite 的 BEGIN IMMEDIATE 锁内等待 GPU。写入时重新检查当天缓存、目录状态及快照版本，以 user_id 加 local_date 的唯一约束裁决并发。竞争请求读取已经提交的推荐。

当天普通账本更新只影响下一日选择；当前卡片保留推荐时点和依据，用户可看到数据已有变化。撤销授权、内容撤回、单集拒绝属于例外，应立即隐藏或终止使用，不继续展示过期内容。理由与所选单集在一次提交中绑定保存。

### 回退与运行方式

数据不足、新用户或模型超时时，使用“财务主题适配加内容语义匹配”的确定性基线，并返回 fallback 原因。大范围数据读取失败则展示可用的基础学习内容或空状态，不生成具体财务判断。

首版在打开今天页面时按需计算，结果每天固定一次。后续可按用户时区预计算活跃用户，浏览时校验缓存；站外通知需要单独的订阅、通知通道和发送实现。

## 5 HSTU 的具体模型实现

### 输入与网络结构

建议将 HSTU 部署为独立的 Python 推理服务，业务后端负责数据权限、快照构建和持久化。训练和推理环境使用 Linux 加 PyTorch；官方仓库的 GPU 依赖需在选定版本上验证，不在当前 Windows Web 进程内直接引入全部训练依赖。[2]

输入包括上下文矩阵 C、内容行为序列 H 和候选集合 I。历史内容向量由单集 ID 嵌入与标题简介的语义向量投影组合；行为类型与时间由对应编码层处理。新单集没有训练 ID 时使用未知 ID 嵌入加内容向量，这是拟开发的冷启动路径。

将财务上下文向量作为前缀，接入官方上下文预处理结构；后面排列内容与行为序列，按所选实现处理时间编码。HSTU 使用因果约束，确保某次预测看不到后来发生的反馈。[3]

用户序列表示与候选内容表示进入评分头，输出多任务预测。候选只使用当前有效目录中的 ID，取效用最高的一项；候选比较必须避免候选之间的信息泄漏。HSTU 编码层按官方实现接入，不以普通 Transformer 命名替代。

### 开发阶段的起始配置

| 参数 | 建议起点 | 调整依据 |
| --- | --- | --- |
| 历史序列长度 | 最近 100 次有效内容事件 | 长短历史组表现与推理耗时 |
| 嵌入维度 | 128 | 验证质量、显存与过拟合情况 |
| HSTU 层数 | 2 | 数据量足够且基线胜出后再扩大 |
| 注意力头数 | 4 | 所选实现的维度兼容约束 |
| 候选数量 | 全量小目录或最多 100 条 | 合格内容覆盖率与延迟 |
| 数据更新 | 每次推荐读取当前快照 | 保证财务事实时效性 |

这些数值是工程试验起点，不是论文要求，也不是已经测得的最优参数。上线需要先完成小数据过拟合检查，确认标签、遮罩和梯度方向正确，再扩大训练。

### 训练目标与模型产物

对实际展示且观察窗口结束的单集，分别训练点击、收藏、有帮助与不感兴趣的二分类任务；缺失或不适用标签用掩码排除。可在同用户有效反馈对足够时增加成对排序损失，首版不默认启用。

总损失为各有效任务损失的加权和加正则项。训练产物同时保存网络权重、特征定义、归一化参数、内容编码器版本和标签规范；发布时整体切换，避免特征与权重不一致。

## 6 训练数据与反馈链路

### 先建立可信的曝光记录

现有 today_for 在返回推荐时写入 exposure，实际含义接近“服务端已提供”。DailyPodcast 在跳转外部单集链接时发送 view，因此 view 只能代表点击，不能代表收听完成。现有收藏与拒绝保存为可覆盖状态，也不足以恢复完整历史训练序列。

拟新增 append-only 的 recommendation_events。每次推荐生成 recommendation_id；服务端先记录 served。前端卡片可见后幂等报告 impression，随后将 click、follow、dislike、helpful_yes、helpful_no 绑定同一推荐 ID。收藏撤销记录为新事件，不覆盖过去状态。

| 事件字段 | 含义与用途 |
| --- | --- |
| event_id 与 recommendation_id | 幂等去重并关联本次推荐 |
| user_key 与 episode_id | 脱敏用户标识和真实内容标识 |
| event_type 与 occurred_at | 明确反馈类型与 UTC 时间 |
| local_date 与 timezone | 还原用户当天的推荐口径 |
| snapshot_id 与 feature_version | 还原推荐当时的财务输入 |
| model_version 与 policy_version | 区分不同模型和选择策略 |
| candidate_set_version 与 score | 审计候选范围和评分 |
| experiment_id 与 selection_probability | 若开展随机试验，记录组别及已知选择概率 |

### 标签与观察窗口

以首次有效 impression 为起点，初始观察窗口可设 72 小时并通过数据调整。点击和收藏在窗口内出现记为正例；窗口结束且埋点链路完整时，“未点击”只可作为点击任务的零标签，不能解释为“不喜欢”。helpful 标签仅接受用户明确作答，未作答不记负例。

明确不感兴趣进入独立负反馈任务。只 served 未展示、跨站行为不可见、数据链路异常等样本不用于相关任务训练。没有外部平台合作或站内播放器数据，就不建立收听时长与完播任务。

### 防止未来数据泄漏

按推荐时间切分训练、验证和测试区间，每个样本只能读取当时已知的财务数据、目标状态、目录版本与历史反馈。目标后续修改和未来收支不能回填到早期输入。训练时保留样本快照，历史数据没有快照时，不用今天的目标状态伪造过去状态。

需要跨用户积累曝光与反馈；单个用户大量账单不等于大量内容偏好标签。初期先运行基线并补齐事件，再训练共享模型。开启 HSTU 的条件由标签覆盖、学习曲线和验证表现决定，不设缺乏依据的固定用户数量门槛。

## 7 工程模块与接口改动

以下路径均相对项目根目录。带“新增”的模块为本方案拟创建内容；当前代码尚未具备这些功能。

| 模块 | 当前作用 | 拟修改内容 |
| --- | --- | --- |
| backend/app/services/podcast_service.py | 兴趣汇总、资格过滤、固定加权和日缓存 | 编排财务快照、候选和模型评分；保留审核校验；将推理移出写事务 |
| backend/app/services/podcast_store.py | 目录、每日推荐、反馈及事件存储 | 增加快照、推荐 ID 和不可变事件表；保留每日唯一约束；采用显式迁移 |
| backend/app/services/user_data_service.py | 收支和用户记录查询 | 新增有边界的滚动窗口查询及完整性标记 |
| backend/app/services/goal_planner.py | 到期现金流与目标资金规划 | 验证可复用口径；补齐交易覆盖和去重后输出推荐所需事实 |
| backend/app/routes/podcast_routes.py | today、feedback 与管理端接口 | 向下兼容返回；新增可见曝光及有帮助反馈校验 |
| src/components/DailyPodcast.js | 今天卡片与外链反馈 | 增加依据展开、有帮助反馈和可见曝光；处理跨日、登录切换及请求过期 |
| src/services/podcasts.js | 前端接口封装 | 携带 recommendation_id；新增反馈类型和幂等键 |
| 新增 finance_context_service.py 与 podcast_ranker.py | 推荐上下文和模型适配 | 统一特征口径、超时与回退；隔离 HSTU 服务协议 |
| 新增 recommendation_training 目录 | 离线数据与训练工具 | 样本构建、训练、评估、模型导出和版本登记 |

### 对外接口约定

GET /api/podcasts/today 保留现有 date、status、program、reason、message、followed 字段，新增 recommendation_id、as_of 和 evidence。evidence 只向本人返回必要依据；模型的原始上下文向量和训练标识不对外暴露。

POST /api/podcasts/feedback 增加推荐 ID 与新反馈类型，并校验推荐归属、内容关联和重复请求。旧的 program_id 加 kind 调用可在迁移期继续使用，但不能伪装成新格式的完整曝光记录。

### 内部推理协议与状态管理

内部 rank 请求包含 feature_version、财务特征与缺失掩码、历史事件、候选 ID 和内容编码版本；响应包含 model_version、候选预测和耗时。请求有最大历史长度、候选上限与超时；版本不兼容时立即回退并报警。

配置开关建议为 PODCAST_RANKER_MODE，支持 baseline、shadow、hstu。shadow 记录 HSTU 结果但向用户返回基线推荐，用于验证服务和评分。现有 SQLite 存储适合单实例起步；多实例共享部署需迁移集中式数据库，不能各自保存每日结果。

## 8 验证与分阶段上线

### 必须证明财务上下文带来价值

设置三个对照：B0 为现有主题规则；B1 为新增财务上下文加内容匹配的基线；B2 为带相同财务上下文的 HSTU。另做一次去掉财务特征的 HSTU 消融实验，区分收益来自序列模型还是财务输入。

按时间留出测试数据，分别报告新用户、新单集、短历史和数据缺失组。离线检查候选覆盖率、NDCG、点击与有帮助任务校准等指标；只有一个正反馈的 Top 1 样本不能支撑全部排序结论。历史日志只看到旧策略选中的内容，离线结果不能替代线上效果证据。

### 线上目标与验收

| 验收项 | 口径或建议门槛 |
| --- | --- |
| 推荐身份与链接 | 所有推荐 ID 均来自有效审核目录；链接与保存单集一致 |
| 每日唯一性 | 同一用户当地日期最多一条已提交推荐；并发和跨日测试通过 |
| 解释正确性 | 金额和期限均可追溯至快照；缺失事实不被补成实际数字 |
| 个性化价值 | 随机对照比较每有效曝光的有帮助肯定率；同时报告反馈响应率与不感兴趣率 |
| 重复与候选覆盖 | 无违反设定冷却期的单集；空状态率和长尾覆盖可观察 |
| 性能与可靠性 | 初始工程目标为已有缓存请求 P95 小于 300 ms、首次计算 P95 小于 2 s；按实测调整 |
| 回退与隐私 | 模型超时、版本错误、撤销授权、账号切换均通过验收 |

表中的延迟值是待验证的工程目标，不是现有性能。A/B 实验按用户随机分组，事先确定主要指标、观察周期和停止条件；样本不足时延长观察，不凭少数点击宣布胜出。站外收听不能作为无数据支持的核心指标。

### 实施顺序与交付物

阶段一完成财务快照、确定性基线、完整埋点和数据授权开关，交付可核对的每日推荐。阶段二形成可重建的时点样本，训练小型 HSTU 并完成时间切分评估与消融。阶段三运行影子模式，验证延迟、错误、版本和候选覆盖。阶段四开展用户随机实验，达到预定条件后逐步扩大流量；异常时切回基线。

### 重点测试场景

包括退款与内部转账、未来到账收入、目标共享资金、已支付未来开支、未知余额、负净结余、记录被删除、内容撤回、近期重复、全部拒绝、模型无返回、重复反馈、UTC 与用户日期不同、跨日并发和登录用户切换。

## 9 场景示例与实施依据

### 用同一用户的财务变化检验推荐

以下为验收用的假设数据，不是任何真实用户记录。用户当前可用余额为 1,800 元，不包含独立存放的目标已存金额；未来 14 日内考试费 500 元、必要生活开支 600 元，应急预留 200 元。期间没有已确认到账收入。

储蓄目标为 2,000 元，独立已存 1,200 元，目标也在 14 日后到期。尚需 800 元；在保护上述开支后，当前可用于目标的金额最多为 1,800 - 500 - 600 - 200 = 500 元，因此在这些假设下仍有 300 元目标缺口。真实使用时必须沿到期时间线计算，不能仅靠总额减法忽略到账时间。

期望的候选为“按到期日安排近期支出”“怎样调整储蓄目标节奏”等主题。固定其他输入后，将未来开支删除或期限后移，相关候选的相对评分应出现可解释变化；实际变化由测试确认，不预先指定 HSTU 必须输出某个单集。

建议的用户理由为：“你记录了近期考试费，同时有一个快到期的储蓄目标。这一期介绍怎样先预留必要支出，再安排目标资金。”展开依据后显示记录范围、快照日期和计算假设，用户可纠正余额或开支状态。

### 数据使用与解释边界

新增针对财务个性化推荐的明确开关与说明；关闭后使用一般学习偏好。原始账本只在获授权的业务服务内处理；推理服务接收必要的结构化特征，训练使用脱敏标识并控制访问、保存期限和删除流程。不得把原始财务数据发给节目发布者。

消费类别和金额表示场景，不能用于推断能力、羞辱消费选择或承诺储蓄结果。理由是可核对的匹配说明，不声称揭示 HSTU 的全部内部决策过程。删除数据或撤销授权后停止新使用，并按既定治理流程清理快照、事件与后续训练样本。
