# 青盈 YouthGain AI 教练专项改进方案

版本：v1.1｜日期：2026 年 10 月 14 日

本次将范围收紧为 AI 教练自身：改进问题理解、知识检索、个人财务依据使用、回复生成、对话体验和回答质量评价。方案为待实施设计。

## 1. 改进目标与范围

**使 AI 教练能够准确承接问题、引用适用资料、解释可复核的计算结果，并在用户需要时提供适量的金融素养引导。**

实施范围为教练接口、教练服务、教练侧检索与校验、聊天界面以及教练专用测试。沿用现有账单、个人资料和财务计算服务，按用户授权只读调用；本次不涉及播客或 HSTU、练习系统、复盘功能、全站学习画像及校园研究平台的改造。

参照 Khanmigo 的计算核验、针对性反馈和回应速度优化，以及 LearnLM 的控制认知负担、适应用户需求原则。这些公开做法提供设计参考，不构成青盈效果的保证，也不意味着存在一个适用于所有任务的“最好教练”。

来源：[Khanmigo 公开实验](https://blog.khanacademy.org/how-khan-academy-is-building-a-better-ai-tutor-our-most-recent-learnings/)、[Google LearnLM 原则](https://blog.google/products-and-platforms/products/education/google-learnlm-gemini-generative-ai/)。

## 2. 当前教练的主要问题

| 当前实现 | 对回复的影响 | 本次改进 |
| --- | --- | --- |
| 以本轮消息进行中文双字词面检索 | 口语表达、同义词和“那怎么办”等追问容易漏检 | 在教练侧进行上下文问题改写与混合检索 |
| 知识按段落截取，每篇取一个片段，最多三篇 | 可能遗漏同一文章中的必要条件和解释 | 增加片段标识、相邻段落补全与候选精排 |
| 个人资料和少量最近记录加入提示词 | 与当前问题无关的信息可能增加干扰 | 只选与本轮任务有关的资料，保留来源与用户更正 |
| 主要靠长提示词约束回复 | 易重复通用建议，解释和引导方式不稳定 | 增加轻量任务路由，分开解释、试算、选择分析与追问策略 |
| 程序计算结果进入模型，但生成后主要检查格式 | 回复仍可能改写数字、混淆余额与结余 | 事实引用、程序渲染和财务口径检查 |
| 独立聊天界面主要展示正文，未消费返回的依据字段 | 用户难以看到具体用了什么资料与数据 | 增加简洁、可展开的本轮依据 |

当前实际链路为 `coach_routes.py → zhipuai_service.py`，知识与计算依据主要由 `coach_evidence.py` 提供。改进沿该链路开展，不需要重构整个应用。

## 3. 改进后的回复流程

**用户问题与相关历史 → 明确本轮任务 → 检索适用知识／调用已有财务工具 → 生成解释与可选引导 → 校验数字和依据 → 展示自然语言回复。**

知识解释无需读取账单；涉及个人计算且用户允许引用记录时才调用个人数据。个人记录读取失败时，保留一般知识解释能力，并明确本次无法计算的项目。

### 3.1 理解问题并承接连续对话

在教练服务中维护本轮话题、已明确条件、用户更正和尚缺信息。上下文首先使用当前会话，不新增跨会话的长期用户画像。

将“那我该怎么办”改写为带明确对象的检索问题，但只能引用此前已出现的信息。例如之前在讨论自动续费，可以改写为“大学生如何检查和调整自动续费订阅”。用户改变话题时及时重置相关状态。

对金额、时间、收入等决定性条件，保留出处并以用户最新明确更正为准。资料不足时先解释能够确定的部分，再问一个最关键的问题；不为每轮机械增加追问。

对于个人金额试算，沿用现有明确金额输入或核对用户新提供的数字，避免把模型猜测直接当作计算参数。新输入与已有资料不一致时说明口径，并确定本轮使用哪组数据。

### 3.2 将基础检索升级为混合检索

仅在教练侧为现有站内知识建立片段索引，不增加知识后台改造要求。

建议算法链路：

1. BM25 关键词召回：处理“最低还款”“机会成本”等精确术语。
2. 语义向量召回：处理“为什么钱总不够花”等口语表达。
3. RRF 排名融合：整合两路候选，避免直接相加不同尺度的分数。
4. Cross-Encoder 精排：联合比较问题和片段，筛选真正回答本轮问题的资料。
5. 适用性检查：保留来源、已有版本或时间信息；补全必要条件，排除不适用资料。

先将 BGE-M3 与中文适用的 BGE reranker 作为候选，在青盈问题集上比较表现、内存和耗时后确定模型。小知识库优先使用本地索引和预计算向量，不必引入新的数据库服务。

可从两路各召回 20 个候选、合并精排、保留 3—5 个片段开始试验；这些是起始配置，需要调参与盲测。片段相关性分数不等于事实可信度概率。

对于无相关资料的通用问题，可以给出一般原理并说明具体事实的缺项；涉及实时政策、利率或条款时，只引用有时效和适用依据的资料，不把模型记忆当作实时核实。

来源：[混合检索与 RRF](https://www.elastic.co/docs/solutions/search/hybrid-search)、[检索与精排](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)、[BGE-M3](https://bge-model.com/bge/bge_m3.html)、[BGE reranker](https://bge-model.com/tutorial/5_Reranking/5.2.html)。

### 3.3 约束个人计算，展示可复核依据

在教练侧封装现有决策、资金与目标服务，形成受控只读工具，不改变账本业务规则。

每次计算返回：输入、单位、公式或计算版本、结果、计算时点、数据覆盖范围及假设。明确区分月均结余、本月可用剩余、估算账户余额与储蓄锁定资金。

关键财务数字分配事实编号，计算卡片及相应标准句由程序渲染；模型通过事实引用组织解释，不自由重写已计算的金额和天数。对模型解释仍检查口径和前后矛盾，不能认为引用了编号就证明语义正确。

新增假设算例必须明确标注并调用受限计算工具核验。没有有效收入、结余不为正或记录不完整时，不编造个人余量和目标延期。

首期由后端根据任务调用工具；需要更灵活调用时再引入模型工具调用。账户身份、参数校验和执行权限由服务端控制，不允许模型执行任意代码、SQL、记账或修改目标。

结构化响应只用于内部处理，前端展示自然语言。当前智谱模型是否具备所需结构化输出与工具调用能力，需要在接入时核对；能力不足时使用服务端校验和模板回退。JSON Schema 合格不等于事实或计算正确。

来源：[工具调用的职责划分](https://developers.openai.com/api/docs/guides/function-calling)、[结构化输出及其局限](https://developers.openai.com/api/docs/guides/structured-outputs)。上述为通用设计参考，不要求改换模型供应商。

### 3.4 改进回答策略，而不是强制教学流程

| 用户需要 | 教练的回答策略 |
| --- | --- |
| 概念解释 | 先直接解释，再给贴近学生生活的例子与适用条件 |
| 财务试算 | 给出程序结果、关键输入与假设，再解释意义 |
| 方案比较 | 按预算压力、必要性、替代方案和机会成本比较；说明倾向的条件 |
| “太泛了／具体一点” | 直接补充操作步骤、检查标准和情境细节，不重复上一轮 |
| 用户愿意学习推理过程 | 对话内给一个适量提示，用户尝试后反馈；可随时请求完整解释 |
| 一般交流 | 正面回答当前问题，不强制转为消费教育 |

教练的金融素养引导覆盖预算、储蓄规划、机会成本、借贷成本、风险和数字金融安全等已有知识能支持的主题。不给用户贴人格或能力标签，也不从消费金额和收入水平推断金融素养。

用户不想作答时直接解释。可选的提示与理解检查在聊天内完成，不新建练习模块，不修改现有选题、评分或复习算法。

示例：用户问“大学生有必要攒钱吗”，先说明攒钱的用途与必要生活开销的优先级，再给能实施的安排方法。用户进一步问“为什么要留应急资金”，解释不确定性与资金可用性；只有用户需要时才提出一个简短理解问题。

### 3.5 增加依据展示与失败回退

在独立聊天页提供“查看本次依据”入口，展示本轮实际采用的知识片段和系统计算。正文保持直接完整，不要求用户阅读资料才能理解答案。

资料引用与结论的对应关系需要校验，不能把全部召回资料都当作支持答案的证据。一般知识、假设例子和个人计算应清楚区分。

保留现有个人记录引用开关；减少发送给外部模型的无关字段。教练内的个人缓存按账户、数据版本和授权范围隔离，公共资料缓存按知识版本更新。

检索或精排失败时回退轻量检索；模型输出不合格时最多修复一次；仍失败则给出已验证计算与模板解释，或明确服务暂不可用。记录失败原因用于排查。

首期优先缩短真实等待时间，限制无关上下文和不必要调用。当前收到完整回复后的打字动画不是流式生成；真正流式展示放到可靠性完成之后，数字与事实须校验后显示。

## 5. 教练自身的评测与验收

将现有 12 条偏标题匹配的检索案例保留为开发检查，新增约 120 条合成或经授权脱敏案例，覆盖口语表达、同义词、连续追问、相反意图、无答案、缺数据、负结余、退款、用户更正和知识中的指令干扰。按题意分组划分调参与盲测集，避免同题换词泄漏。

所有比较走教练真实生产链路。先保持同一生成模型，比较检索与校验升级；再固定检索和工具比较候选生成模型。升级模型通过测试决定，不以“更新”或“更大”直接认定更好。

| 维度 | 验收方法 |
| --- | --- |
| 知识检索 | 比较现有方法、BM25、混合检索、混合检索加精排的 Recall@5 与 nDCG@5；按问题类型报告 |
| 数字与口径 | 与程序真值比对，关键边界用例零未处理错误；此结论只适用于已定义测试集 |
| 资料支持 | 人工盲审关键陈述与所引片段是否对应，检查未核实具体事实 |
| 连续对话 | 正确承接对象、采纳更正、缺项追问有效、不凭空补数据 |
| 教练表达 | 正面回答、步骤具体、语言易懂、提示适量、不反复说教 |
| 可用性 | 测试检索、精排、数据和模型故障回退；记录端到端中位数与 P95 耗时、调用次数和成本 |

可将常规问答 P95 不超过 10 秒列为试用目标，最终以实际部署和体验验证设定门槛；该数值不是现有性能或服务承诺。

在有限范围内邀请用户评价“是否理解解释”“是否获得可执行方法”“是否出现无效追问”。这属于教练体验验证，不扩展为校园教育研究。回答满意度也不能单独证明金融素养提高。

## 6. 实施顺序

1. **第一阶段：回复可靠性。** 统一教练计算依据、补充数值与口径检查、展示本轮依据，建立真实流程回归测试。
2. **第二阶段：检索准确性。** 增加问题改写与 BM25；通过独立评测决定是否加入语义检索和精排。
3. **第三阶段：对话与引导质量。** 拆分任务策略，改善连续追问、用户更正、解释深度和对话内分级提示。
4. **第四阶段：模型与性能优化。** 比较候选模型、调整上下文和缓存、测量延迟与成本，保留可回退版本。

首期的最小交付为：**更准确的回答依据、可复核的个人计算、有效的连续追问和可展开的本轮证据。** 所有升级通过专项盲测后再替换默认教练流程。

## 7. 项目表述

青盈 AI 教练拟采用上下文问题理解、混合知识检索、确定性财务工具和受控生成流程，为青年提供贴近个人情境的金融知识解释与思考引导。通过计算证据、资料追溯及生成后校验提高回复可靠性，并以连续对话、内容准确性和用户理解体验评价改进效果。
