# 每日推荐接口与实施说明

当前工程使用 v2 财务口径；储蓄划拨、不可变快照及机器可读接口定义见 [财务推荐 v2 模块定义](财务推荐v2模块定义.md)。下面保留接口背景；新特征版本为 finance-context-v2。

## 实施计划

1. 保留已有每日唯一约束，新增财务快照表、追加事件表和推荐 ID 索引；兼容已有 SQLite 数据。
2. 新增财务快照服务，区分实际与预计收入，过滤内部转账，保存缺失掩码和缩放特征。
3. 新增 baseline、shadow、hstu 排序适配器，外部 HTTP 推理在数据库写事务之外执行，异常回退基线。
4. 扩展 today、feedback 和可见曝光接口；增加模板理由与本人数据依据。
5. 接入前端曝光、有帮助反馈和依据展示；验证权限、幂等、并发、空候选与超时回退。

## 修改目的与交付范围

将每天一期的内容选择从学习主题匹配扩展为财务情境推荐：在保留内容审核、难度和账号权限检查的基础上，使用用户已记录收支、储蓄目标、未来开支进行排序。推荐理由用模板生成，金额依据绑定生成推荐时的快照，避免把预计收入当成实际到账或把账本结余当成账户余额。

HSTU 是外部序列推荐模型的接入目标。本仓库实现客户端协议、基线、影子比较及回退，不实现 HSTU 网络、训练流水线或权重；外部服务需要另行部署并符合本协议。HTTP 模拟测试验证的是接入行为，不能证明真实 HSTU 的推荐效果。

| 交付物 | 文件 |
| --- | --- |
| 新表、索引、追加约束 | `backend/app/sql/podcast_recommendations.sql` |

| 财务特征快照 | `backend/app/services/finance_context_service.py` |

## 存储和迁移

现有 `daily_picks` 的 `PRIMARY KEY(user_id, local_date)` 继续保证每个用户在其当地日期至多有一条每日记录。已有推荐和空状态当日都直接返回缓存；已收起或失效的推荐当日不会换一条。补齐候选只影响之后日期的选择。

`podcast_store.transaction()` 自动执行新增 SQL；在串行迁移事务中检查列是否存在，再添加旧库缺少的推荐 ID。相当于下面的 SQL，其中 `ALTER TABLE` 只在列不存在时执行：

```sql
ALTER TABLE daily_picks ADD COLUMN recommendation_id TEXT;
CREATE UNIQUE INDEX IF NOT EXISTS daily_picks_recommendation_id
  ON daily_picks(recommendation_id) WHERE recommendation_id IS NOT NULL;
```

新增 `finance_snapshots` 以 `snapshot_id` 为主键，保存 `user_id/as_of/feature_version/payload`，禁止更新和删除。`recommendation_events` 保存事件 ID、推荐 ID、用户、当地日期、内容 ID、事件时间、快照 ID及模型版本，禁止更新和删除。事件主键 `(user_id,event_id)` 保证重试幂等；部分唯一索引保证每条推荐最多一条 `served`。不同曝光、点击和反馈使用不同事件 ID，全部追加；同一事件重试不重复写入。每日唯一约束属于推荐表。

事件分类：`served` 表示推荐已提交，`impression` 表示卡片在可见页面中进入视口，`click` 表示点击收听链接，另有 `follow/dislike/helpful_yes/helpful_no`。旧 `events/feedback` 表继续写入以兼容原有逻辑；曝光统计应使用新表的 `impression`，不能把旧 `exposure` 或 `served` 当成真正展示。

旧每日记录首次访问会补充推荐 ID，保留原始时间及内容；不会补造历史财务快照。此类记录的依据为空、模型版本为 `legacy`，事件的 `snapshot_id` 可以为空。

## 财务快照口径

快照入口 `build_snapshot(user_id, as_of)` 读取该用户账本、目标与学习档案；纯计算入口为 `from_records(...)`。`as_of` 带时区，日期窗口使用用户档案时区，默认 `Asia/Shanghai`。只纳入截至快照时点的实际交易；只有日期的记录按该日期判断。快照保存的是生成推荐时收集到的特征，不是原始账本的历史版本库。

| 特征组 | 字段与口径 |
| --- | --- |
| 已记录实际收入 | `actual_income_month/actual_income_30d`，只计 `transaction_type=income` |
| 已记录净支出 | `net_expense_month/net_expense_30d/net_expense_7d`，支出减退款 |
| 账本结余 | `recorded_surplus_month`，本月已记录实际收入减净支出 |
| 预计收入 | `expected_monthly_income` 来自档案 `monthly_income`；`expected_income_30d` 按 `income_day` 排期，只计今天之后的预计到账，不加入实际收入 |
| 档案金额 | `confirmed_balance/essential_monthly/emergency_buffer`，分别来自 `current_balance/essential_monthly/emergency_buffer`，缺失即未知 |
| 待处理开支 | `upcoming_7d/upcoming_30d/upcoming_count/nearest_upcoming_days`，来自 `kind=upcoming`、未 handled/paid 的记录；今天到今天加 7/30 日，含边界 |
| 储蓄目标 | `active_goal_count/goal_remaining/nearest_goal_days`，只取 active 目标，剩余金额为 `max(target_amount-current_amount,0)` |
| 其他 | `record_count`、`category_net_30d` 和数据完整性 `coverage` |

`transaction_type=transfer`、`receipt_kind=internal_transfer` 等非实际收支记录不计收入或支出。金额先按分计算再转元；拒绝布尔值、负金额、非有限数值及单笔超出 1 亿元的金额。退款用正金额输入，计算净支出时扣除。未来实际交易记录不提前记入到账。

`missing_mask` 中 `1` 表示未知，`0` 表示已观测。缺失原值为 `null`，缩放值为 `0`，必须和掩码一起使用。有效值缩放公式为 `sign(x) * log1p(abs(x))`，负结余保留符号。账本为空、存在无效实际交易或查询失败/达到 10000 条上限时，相应汇总不被声称为完整收支；目标或未来开支来源不完整时也按未知处理。确认完整且没有目标/未来开支可以为零。

对外部排序服务只发送缩放特征、掩码、快照标识、交互序列及内容元数据；不发送用户 ID、原始流水、商户名或备注。快照自身保存在本机配置的 SQLite 数据库。

## 排序、理由与事务

基线保留主题匹配、文本相似度、内容质量、新鲜度和近期主题重复惩罚，并新增财务情境权重：待处理开支提高 buffer 权重、未完成储蓄目标提高 budget 权重、已记录负结余提高 budget 权重。消费类别信号来自同一份已过滤快照。按方案将最近 30 日推荐过的单集硬排除；无新候选时返回空状态。候选还必须通过内容审核、难度、地区、语言、来源时效及不感兴趣检查，并有主题匹配；最多交给排序器 100 个候选。

| 模式 | 用户实际看到的排序 | 外部推理 |
| --- | --- | --- |
| `baseline` | 本地基线 | 不调用 |
| `shadow` | 本地基线 | 调用并把有效得分存入每日记录的 ranking.shadow |
| `hstu` | 有效外部得分 | 超时、连接失败、响应错误或配置错误时回退基线 |

模板理由只引用已有的主题或快照信号。`evidence` 最多两项，包含金额口径、`snapshot_id` 与 `as_of`；未知值不显示。候选为空返回 `status=none/program=null`，不调用外部推理，不编造内容。

流程为：短事务读候选与已存每日记录 → 关闭数据库事务 → 查询财务特征并执行 HTTP 推理 → 短写事务重新检查每日记录、反馈和内容资格 → 原子保存快照、每日推荐和 served 事件。并发请求以已提交的同日推荐为准；推理期间撤回的内容不会被提交。推理不占用 SQLite 写锁。

## HTTP 接口定义

所有接口使用现有 Bearer 登录认证，服务端从登录身份取用户 ID；客户端不传用户 ID。响应保留 `Cache-Control: no-store`。

### GET /api/podcasts/today

旧的 `date/status/program/reason/message/followed` 字段继续保留正常返回形态，新增字段如下。示例中 `program` 省略了原有内容字段：

```json
{
  "date": "2026-10-11",
  "status": "ready",
  "program": {"id": "episode-1", "episode_title": "给生活费留出余地"},
  "reason": "你记录了近期需要预留的开支与“留有余地”有关；这一期聚焦相关的具体问题。",
  "message": null,
  "followed": false,
  "helpful": false,
  "recommendation_id": "推荐 UUID",
  "as_of": "2026-10-11T12:00:00+08:00",
  "timezone": "Asia/Shanghai",
  "evidence": [{
    "feature": "upcoming_30d",
    "label": "未来30日已记录待处理开支",
    "value": 500.0,
    "unit": "元",
    "snapshot_id": "快照 UUID",
    "as_of": "2026-10-11T12:00:00+08:00"
  }]
}
```

`status` 可为 `ready/none/dismissed/unavailable`。后三种无可收听内容时 `program=null`；空候选 `evidence=[]`。`helpful` 按当前推荐的最新 helpful 事件计算，不从同内容的其他日期继承。

### POST /api/podcasts/feedback

旧请求 `{"program_id":"episode-1","kind":"follow"}` 继续支持；未指定推荐 ID 时关联本人最近一次该内容的每日记录。建议新客户端绑定精确推荐并发送幂等 ID：

```json
{
  "program_id": "episode-1",
  "recommendation_id": "推荐 UUID",
  "event_id": "本次操作 UUID",
  "kind": "helpful",
  "value": true
}
```

`kind` 支持 `view/follow/dislike/helpful/impression`；可见曝光建议走下方 events 接口。helpful 必须绑定本人 recommendation_id；旧 view/follow/dislike 请求保持兼容。`value` 只对 helpful 生效，默认 true，必须为布尔值；false 追加 `helpful_no`，不删除历史 `helpful_yes`。响应：

```json
{"feedback":{"program_id":"episode-1","kind":"helpful","saved":true,"recommendation_id":"推荐 UUID","event_id":"本次操作 UUID"}}
```

同一用户重试同一事件 ID、同一推荐、同一类型会成功返回原事件，不反向覆盖较新的反馈；同一个事件 ID 被用于其他推荐或类型返回 409。反馈历史只追加，当前 follow/dislike 状态继续维护旧表。

### POST /api/podcasts/events

```json
{
  "program_id": "episode-1",
  "recommendation_id": "推荐 UUID",
  "event_id": "impression:推荐 UUID",
  "kind": "impression"
}
```

成功响应形状为 `{"event":{...}}`，内部字段同 feedback。另一个设备的实际曝光使用新的事件 ID，追加新的曝光记录。相同事件 ID 重试返回原事件；推荐 ID 必填且必须属于当前用户与内容。

| HTTP 状态 | 含义 |
| --- | --- |
| 200 | 成功或幂等重试 |
| 400 | 字段、反馈类型、JSON 或 helpful 值无效 |
| 401 | 未登录或认证失败 |
| 404 | 推荐不属于本人、内容 ID 不对应，或曝光内容已不可查看 |
| 409 | 事件 ID 被用于不同推荐或类型 |
| 503 | SQLite/本地服务不可用；外部推理失败通常回退后仍返回 200 |

## 外部 HSTU 服务协议与配置

在后端环境中配置（默认 baseline 可直接运行）：

```dotenv
PODCAST_RANKER_MODE=shadow
PODCAST_HSTU_URL=http://127.0.0.1:9090/rank
PODCAST_HSTU_API_KEY=
PODCAST_HSTU_TIMEOUT_SECONDS=2
```

URL 只来自可信服务配置；支持 HTTP/HTTPS，不跟随重定向。API key 非空时发送 `Authorization: Bearer ...`。超时配置须大于 0 且不超过 30 秒，连接超时最多 1 秒，读取超时为配置值；读取分块时也检查累计耗时及 64 KiB 响应上限。

POST JSON 示例（features 和 missing_mask 实际包含全部快照特征）：

```json
{
  "feature_version": "finance-context-v1",
  "snapshot_id": "快照 UUID",
  "as_of": "2026-10-11T12:00:00+08:00",
  "features": {"upcoming_30d": 6.216606101, "confirmed_balance": 0.0},
  "missing_mask": {"upcoming_30d": 0, "confirmed_balance": 1},
  "history": [{"program_id":"episode-previous","action":"helpful_yes","occurred_at":"2026-10-10T03:00:00+00:00"}],
  "candidates": [{"program_id":"episode-1","topics":["buffer"],"title":"给生活费留出余地","summary":"预留未来账单的金额。","baseline_score":0.8}]
}
```

历史只取当前用户、快照时间之前的最多 100 条点击与反馈事件，按时间顺序发送；不把 served/impression 当作正向兴趣反馈。响应必须是 HTTP 200：

```json
{"model_version":"hstu-service-v1","scores":[{"program_id":"episode-1","score":0.93}]}
```

每个候选须有且仅有一个有限数值得分，分数越大越优先；禁止新增候选、缺失候选、重复 ID、布尔分数或 NaN/Infinity。`model_version` 必须为 1–100 字符的非空字符串。外部服务可以在适配层将本协议转为其实际 HSTU 输入，本项目不假设某个现成服务天然支持此协议。响应校验失败会回退并在每日记录 ranking 中记录原因。

## 前端修改片段

真实改动已写入组件和 API 服务，下面概括新客户端调用：

```javascript
// 卡片至少 10% 进入视口且页面可见时上报；服务端按推荐去重。
await sendPodcastImpression(result.program.id, result.recommendation_id);

// 有帮助反馈必须绑定本次推荐；同一次网络重试应复用同一个 event_id。
await sendPodcastFeedback(result.program.id, 'helpful', {
  recommendation_id: result.recommendation_id,
  event_id: window.crypto.randomUUID(),
  value: true,
});
```

组件使用 IntersectionObserver，监听页面可见性，避免后台页面被计为曝光；保留账号切换后的响应隔离。新增“对我有帮助”按钮、可展开的依据金额及时间说明，跨日刷新使用后端返回的用户时区。旧 today 响应缺少推荐 ID 时仍可展示及发送旧反馈。

## 验证与接入步骤

测试使用合成账户、内容与模拟 HTTP，不读取真实用户财务信息。自动验证覆盖财务口径、缺失与缩放、账号隔离、曝光去重、反馈幂等、并发每日唯一、事务外推理、内容撤回、三种排序模式、超时及无效响应回退，以及前端展示与可见曝光。

先以 baseline 启动，可在首次请求时完成增量迁移。接好外部服务后切到 shadow，检查排名响应和模型版本，再用离线评价或受控线上对照决定是否切到 hstu；切换配置不会重排当天已经提交的推荐。

2026-10-13 验证结果：后端推荐、快照、账本和学习接口合计 71 项测试通过；SQL 整理后的推荐专项 34 项再次通过；前端卡片 4 项通过（包含页面隐藏时不计曝光）；生产构建成功。构建仍报告其他页面原有的未使用变量、链接及包体积提示，本次推荐组件没有新增构建检查警告。HSTU HTTP 使用模拟服务验证，尚未连接实际部署的模型。
